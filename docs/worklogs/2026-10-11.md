## ⚠️ 重大发现：UI 单章生成不走 sepia（sepia 只在批量流水线上生效）
用户问「UI 上执行小说章节生成会调用 sepia 吗」。逐层追代码 + 运行时日志验证，结论：**分两种 UI 入口，行为不同**。

### 入口 A：质量修复 tab 的「执行流水线」（批量）→ ✅ 走 sepia
- 前端 `production.ts:38` → `POST /novels/:id/pipeline/run`（payload 带 sepiaDeAi）
- → `NovelPipelineExecutor`(L630) → `chapterRuntimeCoordinator.runPipelineChapter` → `ChapterPipelineRuntimeAdapter.runPipelineChapter` → **`runPipelineChapterWithRuntime`**（`chapterRuntimePipeline.ts`）→ L277 `if (sepiaDeAi && content.trim())` → `runSepiaDeAi`
- 这是**唯一**能触发 sepia 的路径。

### 入口 B：章节页「生成本章正文」按钮（单章 SSE）→ ❌ 不走 sepia
- 前端 `useNovelEditChapterRuntime.ts:152` → `POST /novels/:id/chapters/:chapterId/generate`（body 只有 provider/model/previousChaptersSummary，**不传 sepiaDeAi**）
- → `novelChapterGeneration.ts` 路由 → `stepModuleRunner.runStep(chapter_execution)` → `ChapterExecutionStageRunner`(L85) → `coordinator.createChapterStream` → `ChapterWritingGraph.createChapterStream`（**直接流式写正文**）
- **不经过 `NovelPipelineExecutor`，也不经过 `runPipelineChapterWithRuntime`** → 无 sepia。
- 另一条 `POST /novels/:id/chapters/:chapterId/runtime/run` 同理。

### 根因（两个独立问题）
1. **`chapterRuntimeRequestSchema`（`server/src/services/novel/runtime/chapterRuntimeSchema.ts`）没有 `sepiaDeAi` 字段**，且是普通 z.object（默认 strip），即使前端传了也会被剥掉。
2. **`createChapterStream` 这条链根本不经过 sepia 接入点**——sepia 只插在 `chapterRuntimePipeline`（批量路径的专用管线）里。

### 判定方法（可复用）
- `runPipelineChapterWithRuntime` 的唯一调用者是 `ChapterPipelineRuntimeAdapter`；`runPipelineChapter` 的唯一调用者是 `NovelPipelineExecutor` L630。所以「是否走 sepia」⇔「是否经过 NovelPipelineExecutor」。
- 运行时验证：查 `.logs/YYYY-MM-DD/*.jsonl` 的 `"stage":"sepia_architecture|sepia_discourse|sepia_surface"`。实测 15:58 那次是**我的验证脚本**产生的（非 UI）；用户 UI 跑的那次（23-58-18 日志，跨 5 分钟）只有 `auto_director/market_radar/story_macro/structured_outline/volume_strategy/payoff_ledger_planning`，**全是规划阶段，无 chapter_writer 也无 sepia**。
